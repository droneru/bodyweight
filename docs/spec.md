# Bodyweight — спецификация

Сервис учёта силовых тренировок. Пользователь записывает тренировки и взвешивания, а сервис показывает его рекорды в стандартных упражнениях за последние 90 дней и за всё время.

Термины определены в [CONTEXT.md](../CONTEXT.md). Здесь используются русские термины, в скобках — канонические английские.

## 1. Доменная модель

### 1.1 Тренировка (Workout)

- Принадлежит одному пользователю.
- **Дата** — только дата, без времени. В одну дату может быть несколько тренировок. Даты в будущем запрещены.
- **Заметка** (Note) — необязательный произвольный текст.
- Упорядоченный список **выполнений упражнений** (Exercise Entry).

### 1.2 Выполнение упражнения (Exercise Entry)

- Ссылается на упражнение из каталога.
- Порядок выполнений внутри тренировки важен.
- Одно и то же упражнение может встретиться в тренировке несколько раз.
- Содержит упорядоченный список подходов.

### 1.3 Подход (Set)

- **Повторы** (Reps) — целое число ≥ 1.
- **Вес снаряда** (Weight) — необязателен. Задаётся в килограммах, дробный, с шагом 0.25. Если веса нет, подход выполнен с собственным весом.
- Порядок подходов важен.
- Каждый подход хранится отдельной записью. «Три подхода 5 × 70 кг» — это три записи.

Пример: тренировка «жим лежа + приседания». Приседания — подход 5 × 60 кг, затем три подхода 5 × 70 кг.

### 1.4 Упражнения (Exercise)

- **Стандартные упражнения** (Standard Exercise) задаются в коде: подтягивания и **большая тройка** (Big Three) — жим лежа, приседания, становая тяга. Только для них считаются рекорды.
- **Пользовательские упражнения** (Custom Exercise) пользователь заводит сам:
  - видны только автору;
  - их можно переименовать;
  - удалить можно только упражнение, которое не используется ни в одной тренировке. Используемое можно архивировать, тогда оно скрывается из выбора, но остаётся в старых тренировках;
  - рекорды для них не считаются.

### 1.5 Взвешивание (Weigh-in)

- Дата и вес тела в кг с точностью 0.1.
- Не больше одного взвешивания на дату. Новое взвешивание в ту же дату заменяет старое.
- Дата может быть в будущем не больше чем на 2 дня от сегодняшней даты сервера (Europe/Moscow). Запас нужен пользователям, у которых местная дата опережает серверную.

### 1.6 Доля от веса тела (Bodyweight Ratio)

- Считается для каждого подхода с весом в любом упражнении.
- `доля = вес снаряда / вес тела`, округляется **вниз** до десятых. Пример: жим лежа 1.2 веса тела.
- Вес тела берётся из последнего взвешивания на дату тренировки или раньше. Если такого взвешивания нет, доля не показывается.
- Показывается только при просмотре тренировки. В рекордах доли нет.

## 2. Рекорды (PR)

Рекорды вычисляются при каждом запросе и не хранятся.

### 2.1 Периоды (Period)

- **90 дней**: тренировки с датой в диапазоне `[сегодня − 89 дней, сегодня]`.
- **Всё время**.
- «Сегодня» считается в часовом поясе Europe/Moscow.

### 2.2 Правила расчёта

| Упражнение | Мера | Какие подходы участвуют |
|---|---|---|
| Подтягивания | Рекорд повторов (Max Reps): максимум повторов в одном подходе | Только подходы без веса снаряда |
| Большая тройка (Big Three): жим лежа, приседания, становая тяга | Расчётный 1ПМ (Estimated 1RM): максимум по подходам | Подходы с весом и не больше 12 повторами |

Расчётный 1ПМ считается по формуле Эпли: `1ПМ = w × (1 + r / 30)`, где `w` — вес снаряда, `r` — повторы. При `r = 1` берётся сам вес `w`.

Пример: за период были подходы 100 × 1 и 90 × 10. Рекордом станет 90 × 10 с расчётным 1ПМ 120.

Если за период в упражнении нет подходящих подходов, рекорда нет и в интерфейсе ставится прочерк.

Если несколько подходов дают одинаковое значение, берётся самый ранний по дате.

### 2.3 Представление

Ячейка рекорда содержит:
- для большой тройки — расчётный 1ПМ, исходный подход и дату. Пример: `120 kg — 90×10, 2026-10-12`;
- для подтягиваний — число повторов и дату.

## 3. Пользователи и аутентификация

- Вход через **OAuth Яндекс ID**. Регистрация открытая: войти может любой с аккаунтом Яндекса.
- Пользователь идентифицируется Яндекс-логином. Из профиля сохраняются Яндекс UID, логин, отображаемое имя и идентификатор аватара, если аватар есть. Email не запрашивается и не хранится.
- У приложения в Яндекс OAuth запрошены права `login:info` и `login:avatar`.
- Сессия хранится на сервере в YDB, браузер держит её в httpOnly secure cookie. В YDB лежит не само значение cookie, а его SHA-256.
- Залогиненному пользователю в шапке показываются аватар (или первая буква логина, если аватара нет), логин и кнопка «Log out». Кнопка «Sign in with Yandex ID» при этом скрыта.
- Срок жизни сессии скользящий, 30 дней.
- Кнопка «Log out» удаляет сессию на сервере.
- **Dev-логин**: если задана env-переменная `BODYWEIGHT_DEV_LOGIN=1`, доступен эндпоинт входа под произвольным логином без OAuth. Он используется в `make dev` и в интеграционных тестах. В продакшене выключен.

## 4. Веб-приложение

- Вёрстка в первую очередь под мобильный телефон.
- Интерфейс только на английском.

### 4.1 Экраны

1. **Workouts** — список тренировок, новые сверху. В строке: дата, упражнения и начало заметки, сколько помещается по ширине экрана.
2. **Workout** — просмотр и редактирование тренировки: дата, заметка, выполнения и подходы. У подходов с весом показывается доля от веса тела.
3. **PRs** — таблица: стандартные упражнения × {90 days, All time}.
4. **Weigh-ins** — список взвешиваний, новые сверху, и добавление нового. Дата по умолчанию — сегодняшняя по локальному времени браузера. Вес можно ввести и с запятой, и с точкой.
5. **My exercises** — пользовательские упражнения: создать, переименовать, архивировать, удалить.

### 4.2 Добавление упражнения в тренировку

1. Пользователь выбирает упражнение.
2. Интерфейс находит последнее выполнение этого упражнения: в тренировке с самой поздней датой, а внутри неё — последнее по порядку. Текущая тренировка не учитывается.
3. Подходы из найденного выполнения предлагаются как **предложенные подходы** (Suggested Set) с теми же повторами и весом.
   - Слева у каждого — отметка «сделано», изначально снята.
   - Повторы и вес можно изменить.
   - Справа — кнопка удаления.
4. Сохраняются только отмеченные подходы. Неотмеченные — нет.
5. Если упражнение ещё ни разу не выполнялось, показывается одна пустая строка подхода.
6. Кнопка **«Repeat set»** добавляет копию предыдущего подхода.

Пример: пользователь выбирает жим лежа. В прошлый раз было 3 подхода по 3 повтора с весом 70 кг. Интерфейс предлагает три строки 3 × 70.

### 4.3 Сохранение

- Автосохранение: тренировка создаётся сразу, каждое изменение тут же уходит на сервер.
- Если сеть недоступна, изменения хранятся в localStorage. Интерфейс показывает статус «not saved» и повторяет отправку.
- Дата новой тренировки по умолчанию — сегодняшняя по локальному времени браузера.

## 5. CLI

Админская утилита для тех, у кого есть прямой доступ к базе.

- Работает **напрямую с YDB** и использует тот же crate хранения, что и сервер.
- Параметры подключения берутся из стандартных env-переменных YDB SDK: `YDB_ENDPOINT`, `YDB_DATABASE`, `YDB_SERVICE_ACCOUNT_KEY_FILE_CREDENTIALS` / `YDB_ACCESS_TOKEN_CREDENTIALS`.
- Пользователь задаётся env-переменной `BODYWEIGHT_USER` (Яндекс-логин).
- Сообщения только на английском.
- Функции такие же, как у веб-интерфейса:
  - создать тренировку, добавить в неё выполнение упражнения и подходы;
  - посмотреть список тренировок;
  - посмотреть список упражнений;
  - посмотреть текущие рекорды;
  - посмотреть список взвешиваний (`bodyweight weigh-ins list`) и добавить взвешивание (`bodyweight weigh-ins add 82.5 [--date YYYY-MM-DD]`). Дата по умолчанию — сегодняшняя в часовом поясе Europe/Moscow.
- Предложенных подходов в CLI нет.

## 6. Архитектура и стек

- Бэкенд и CLI: Rust, axum.
- Хранилище: YDB. В продакшене — Serverless YDB (Yandex Cloud), в тестах и разработке — YDB в docker-контейнере.
- Фронтенд: TypeScript, React, Vite. Собранная SPA раздаётся сервером.
- Интерфейс собирается из компонентов [shadcn/ui](https://ui.shadcn.com) на Base UI со стилями Tailwind CSS. Исходники компонентов лежат в `web/src/components/ui` и добавляются командой `npx shadcn@latest add <component>` из `web/`. Тема только тёмная, палитра задана в `web/src/styles.css`.
- Один docker-образ: axum раздаёт SPA и API под `/api`.

### 6.1 Структура репозитория

```
Cargo.toml           Rust workspace
crates/domain        доменная модель, расчёт рекордов и доли от веса тела (без IO)
crates/storage       работа с YDB
crates/server        axum: API, OAuth Яндекс ID, сессии, раздача SPA
crates/cli           админский CLI
web/                 React + TypeScript (Vite)
migrations/          YQL-миграции схемы (goose)
deploy/              Dockerfile, docker-compose.yml, docker-compose.dev.yml (make dev)
Makefile
```

### 6.2 Схема БД и миграции

- Миграции — версионированные YQL-файлы в `migrations/`. Применяются через [goose](https://github.com/pressly/goose), который поддерживает YDB и запускается из docker-образа.
- Сервер при старте схему не меняет.
- Миграции запускаются отдельно (`make migrate`) до деплоя.

## 7. Сборка, тесты, make

| Цель | Что делает |
|---|---|
| `make test` | Unit-тесты Rust и фронтенда (vitest) |
| `make integration-test` | Поднимает YDB в docker, применяет миграции, гоняет интеграционные тесты, останавливает YDB |
| `make docker` | Собирает docker-образ веб-приложения |
| `make cli` | Собирает CLI (release) |
| `make migrate` | Применяет YQL-миграции через goose к YDB из env-переменных `YDB_ENDPOINT`, `YDB_DATABASE`, `YDB_ACCESS_TOKEN_CREDENTIALS` (IAM-токен) |
| `make dev` | Локальный запуск: YDB в docker с применёнными миграциями, сервер с dev-логином, vite dev server |
| `make dev-env` | Печатает env-переменные для подключения CLI к YDB из `make dev` |
| `make dev-ydb` | Открывает ydb CLI на YDB из `make dev`: интерактивный YQL, либо команда из `ARGS` |
| `make dev-down` | Останавливает dev-окружение, данные YDB сохраняются |
| `make dev-clean` | Останавливает dev-окружение и удаляет данные YDB |
| `make lint` | `cargo fmt --check`, `cargo clippy`, eslint, prettier |
| `make deploy` | На VPS: `git pull && docker compose up -d --build` |

### 7.1 Тесты

- **Unit**: доменная логика (рекорды, расчётный 1ПМ, доля от веса тела, окно 90 дней) и фронтенд.
- **Интеграционные**: используют YDB в docker-контейнере и покрывают слой хранения и HTTP API сервера. Для входа используется dev-логин. CLI отдельно не тестируется, потому что работает через тот же crate хранения.

### 7.2 Docker-образ

- Multi-stage Dockerfile. Вся сборка (SPA через node, сервер через Rust) идёт в первой фазе внутри docker. Хосту нужен только docker, без Rust и node.
- Финальный образ минимальный: бинарник сервера и статика SPA.

## 8. Развёртывание

- Домен **bodyweight.ru**. `www` не поддерживается.
- VPS с docker compose: контейнер приложения за общим для сервера **caddy** (HTTPS, автоматические сертификаты, роутинг по домену), связь через внешнюю docker-сеть `proxy`.
- База — Serverless YDB, параметры подключения передаются через env. Приложение ходит в неё от имени сервисного аккаунта (sa) с ролью `ydb.editor`, авторизованный ключ sa лежит на VPS в `deploy/secrets/sa-key.json`.
- Секреты и параметры продакшена лежат на VPS в `deploy/.env` (образец — `deploy/.env.example`) и в git не попадают.
- Образ собирается прямо на VPS из клона репозитория (`make deploy`).
- CI/CD пока не описывается.
